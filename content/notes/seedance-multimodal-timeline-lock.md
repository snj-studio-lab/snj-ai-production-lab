# Seedance를 2패널 정지 컷 도구로 쓰면 안 되는 이유

## 요약

이 글은 AI 영상 제작 워크플로우에서 반복적으로 발생한 한 가지 문제를 정리한다.

> 최신 멀티모달 영상 생성 도구를 쓰면서도, 실제 실행 단계에서는 그 도구의 장점을 거의 쓰지 못하는 방식으로 프롬프트가 작성되는 문제.

문제는 단순히 프롬프트가 길거나 짧은 것이 아니었다.

더 큰 문제는 다음 세 가지였다.

```txt
1. 스토리보드가 선택사항처럼 취급됨
2. 12~15초 클립이 컷 수 기준으로 균등분할됨
3. 긴 내부 REF_ID가 실제 실행 프롬프트에 그대로 노출됨
```

이 세 가지가 겹치면, 제작자는 멀티모달 도구를 쓰고 있지만 결과물은 정적인 2패널 요약, evidence board, 분할 화면, 또는 내부 작업표 같은 형태로 무너진다.

## 왜 이 문제가 생겼나

AI 영상 제작 파이프라인은 보통 여러 단계로 구성된다.

```txt
대본
→ 컷 구조
→ 레퍼런스 이미지
→ 스토리보드 / 그리드
→ 실행 프롬프트
→ 영상 생성
→ 검수
```

각 단계의 목적은 다르다.

하지만 실제 작업표에서는 이 구분이 자주 무너졌다.

예를 들어, 스토리보드 이미지를 생성해야 하는 칸에 실제 패널 프롬프트가 아니라 정책 메모가 들어가거나, 실행 프롬프트가 장면 지시문이 아니라 내부 엔진 로그처럼 변하는 문제가 생겼다.

이 경우 제작자는 “지침을 따랐다”고 생각하지만, 실제 영상 생성 도구는 필요한 장면 정보를 받지 못한다.

## 스토리보드는 선택사항이 아니다

멀티모달 영상 생성 도구를 쓰는 이유는 텍스트만으로는 전달하기 어려운 장면 흐름을 이미지로 함께 전달하기 위해서다.

스토리보드나 16패널 그리드는 단순 장식이 아니다.

그것은 다음 정보를 압축한다.

```txt
- 장면 순서
- 주체의 위치
- 카메라 방향
- 움직임의 시작과 끝
- 감정 변화
- 시각적 payoff
- 공간 관계
```

따라서 스토리보드 기반 워크플로우에서 가장 위험한 문장은 이런 것이다.

```txt
스토리보드는 위험하면 생략한다.
```

이 문장은 작업자에게 매우 편한 탈출구가 된다.

하지만 결과적으로는 멀티모달 도구를 텍스트 프롬프트 도구처럼 쓰게 만든다.

더 안전한 원칙은 다음이다.

```txt
스토리보드는 기본 실행 구조다.
문제가 생기면 스토리보드를 제거하는 것이 아니라, 스토리보드를 고친다.
```

## 2패널 기본값의 문제

짧은 대사, 단일 반응, 단순 전환은 2~3패널로 충분할 수 있다.

하지만 변형, 추격, 붕괴, 시간 전환, 물리적 payoff, 이상현상 progression이 있는 장면을 2패널로 줄이면 장면의 핵심이 사라진다.

나쁜 방식:

```txt
15초 클립
P1: 시작
P2: 끝
```

이 방식은 모델에게 “중간 과정”을 거의 전달하지 않는다.

좋은 방식:

```txt
15초 클립
P1: 접근
P2: 이상 징후 발생
P3: 주체 반응
P4: 공간 변화
P5: 시각적 payoff
P6: 후속 반응 또는 다음 장면 연결
```

일반적인 cinematic progression에는 4~6패널이 더 적합하다.

시각 변형이나 물리적 사건이 있는 장면은 5~8패널을 먼저 검토해야 한다.

16패널 ACTION_AUX는 고밀도 액션, 추격, 격투, 붕괴, 다단계 물리 움직임에 적합하다.

## 15초를 컷 수로 나누면 안 된다

또 다른 실패는 시간 배분에서 발생한다.

나쁜 방식:

```txt
15초 / 5컷 = 각 3초
```

이 방식은 장면의 기능을 보지 않는다.

대사 컷, 시각 payoff, 반응 컷, 액션 컷은 필요한 시간이 다르다.

좋은 방식은 beat function 기준으로 시간을 배정하는 것이다.

```txt
setup: 1.5초
action begins: 2초
dialogue: 4.5초
visual payoff: 5초
reaction / end beat: 2초
```

시간은 컷 수가 아니라 다음 요소를 기준으로 배정해야 한다.

```txt
- 실제 대사 길이
- 발화 속도
- lip-sync 부담
- 액션 / 리액션 복잡도
- 시각 변형 밀도
- silent payoff 길이
- 감정 pause
- 카메라 이동 필요성
```

## 긴 REF_ID는 실행 프롬프트를 오염시킨다

제작 시스템 내부에서는 긴 canonical ID가 유용할 수 있다.

예:

```txt
COMMON_AGENT_JIN
ENV_M47_TUNNEL_INTERIOR
ENTITY_PREHISTORIC_MASSIVE_PARTIAL
```

하지만 실제 실행 프롬프트와 사용자 작업표에서는 이런 긴 ID가 문제를 만든다.

```txt
- 3,500자 제한을 낭비함
- UI에서 잘림
- 첨부 파일 구분이 어려워짐
- 프롬프트가 내부 관리 문서처럼 보임
- 실제 장면 지시보다 메타데이터가 더 많아짐
```

실행 단계에서는 짧은 alias가 필요하다.

```txt
A_JIN
E_M47I
O_ENT
```

권장 prefix는 다음과 같다.

```txt
A_  = Actor / named human / speaking subject
E_  = Environment / location / set
V_  = Vehicle / vehicle interior / transport
EQ_ = Equipment / weapon / operated device
O_  = Object / entity / anomaly / creature
G_  = Group / crowd
FX_ = Visual effect / phenomenon
```

핵심 원칙:

```txt
긴 canonical ID는 내부 registry에 둔다.
실제 작업표와 실행 프롬프트에는 짧은 alias만 쓴다.
```

## 공개 가능한 교훈

이 실패에서 얻은 공개 가능한 교훈은 단순하다.

```txt
1. 멀티모달 도구를 쓴다면, 멀티모달 입력을 기본 구조로 삼아야 한다.
2. 스토리보드가 문제를 일으키면 생략하지 말고 고쳐야 한다.
3. 2패널은 기본값이 아니라 예외다.
4. 12~15초는 컷 수가 아니라 beat function으로 배분해야 한다.
5. 내부 관리용 ID와 실행용 alias는 분리해야 한다.
6. 작업표는 내부 엔진 로그가 아니라 제작자가 실제로 사용할 실행 문서여야 한다.
```

## 체크리스트

새로운 Seedance 실행 패키지를 검수할 때는 먼저 아래만 확인한다.

```txt
1. 스토리보드 이미지 프롬프트가 실제 패널 프롬프트인가?
2. 실행 프롬프트에 @Image1 P# 흐름이 살아 있는가?
3. 각 패널 / 컷에 Active subject가 명확한가?
4. 2패널이 기본값처럼 반복되고 있지 않은가?
5. 12~15초가 컷 수로 균등분할되어 있지 않은가?
6. 대사 길이와 silent payoff 시간이 반영되어 있는가?
7. 긴 canonical REF_ID가 실행 프롬프트에 노출되어 있지 않은가?
8. 짧은 alias가 일관되게 쓰였는가?
9. 내부 정책문이 프롬프트 칸에 들어가 있지 않은가?
10. 최종 영상이 panel sheet가 아니라 full-screen cinematic footage로 변환되도록 지시되어 있는가?
```

## 최종 문장

AI 영상 제작에서 지침은 많을수록 좋은 것이 아니다.

중요한 것은 지침이 실제 도구의 목적을 지키게 만드는 것이다.

Seedance 같은 멀티모달 영상 도구를 쓰는 이유는 단순한 텍스트 생성이 아니라, 스토리보드와 레퍼런스를 통해 장면의 흐름을 전달하기 위해서다.

따라서 이 워크플로우의 핵심은 다음 한 문장으로 정리된다.

> 스토리보드는 생략할 위험요소가 아니라, 고쳐서 사용해야 할 제작 구조다.
